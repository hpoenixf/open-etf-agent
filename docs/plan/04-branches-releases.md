# 04 · 一期一分支，每版独立运行

> R2保留原分支策略。本次只更新方案PR；没有已发布版本，没有创建未来phase分支或标签。命令为未来目标。

## 1. 四种引用

| 引用 | 用途 | 维护规则 |
| --- | --- | --- |
| main | 最近验收版本和评审后的文档/修复 | 不合入下一期半成品 |
| phase/v0.1 … phase/v1.0 | 本期完整代码，开发后保留 | 发布后冻结功能，只接必要patch |
| v0.1.0 … v1.0.0 | 已验证的精确发布点 | 不移动、不覆盖；修复发新patch标签 |
| fix/vX.Y-topic、docs/topic | 短期修复或文档提案 | 不等于软件已发布 |

下一期沿上一期主线累计演进，分支独立包含全部源码和依赖，不是只存本期增量。固定标签便于文章复现；分支可前进，标签不移动是维护纪律，不是Git天然保证。

本次尚无发行，所以可以修订未来版本范围；若将来已经发布，不能重新定义旧v0.3的含义，应在新版本修正并保留旧史。

## 2. 每期流程

1. 检查main、前一标签、已有修改和差异，从已验收基线创建本期phase分支。
2. 完成本期和累计案例，删除替代路径，更新准确说明；允许中途提交，不提前声明released。
3. 固定候选SHA，运行受影响契约与累计关键交接，记录失败/未验证。
4. 提交phase到main的PR，说明新增/删除、兼容、验收；保留教学演进的可追踪提交关系。
5. 合并结果上复核安装、构建和默认案例，通过后才创建版本标签/Release。
6. 将phase分支快进到实际发布提交并保留；发现分歧先对账，不强推覆盖。

每个阶段可以有多个小实现PR，但只有完整通过的阶段才作为读者可运行版本发布。当前方案PR不授权自动开发十期、合并或发布。

## 3. 独立运行的条件

每个标签都含源码、自己的fixture、依赖锁、环境/支持平台、配置示例、测试、默认demo和live入口。不得依赖私人ETF仓库、书稿PDF、相邻worktree、其他phase的源码、运行时下载最新main、隐式私有API或真实账户。

建议早期保持统一外层入口：npm ci/build/test/demo。新增命令按行为出现：v0.3初版observe，v0.5显式memory操作，v0.6serve/evaluate，v0.7inspect/resume/cancel，v0.8web/background。早期取消由进程内信号提供，不伪装成跨进程cancel命令。

默认demo安装依赖后可离线。live只在明确选择时运行，无凭据就说明不可用，不回退替身伪造成功。每次输出标明版本、case、模型模式、结果位置和当前边界。

研究配置可需要容器/解析器；缺少环境不能算该配置通过，也不能阻塞无此能力的早期标签。

## 4. 相邻版本怎么演示

发布后可使用独立worktree运行共同案例，再运行本期新增case：

```bash
# 仅在这些标签实际发布后执行。
git fetch origin --tags
git worktree add --detach ../open-v01 v0.1.0
git worktree add --detach ../open-v02 v0.2.0
# 分别进入目录，按该标签README安装并运行document-compare。
git diff v0.1.0..v0.2.0 -- src examples tests docs/evolution
```

文章至少有共同任务、一个新能力任务、一条失败路径和实际diff。不能用两个完全不同问题的输出宣称性能提升，也不能在v0.1预埋全部能力再依次打开开关。

## 5. 环境与数据

在实现时选仍受支持的运行时并锁定精确版本/lockfile；PDF中的Node/SDK数值只说明教材环境，不自动成为本仓库兼容承诺。历史标签不追随最新依赖改写；必要修复发patch。

每个版本使用独立state目录。v0.1起保存的报告可以读；v0.7起的checkpoint才有原Run恢复合同。迁移文档必须分别写“旧报告读取”“记忆格式转换”“活跃Run接续”，不能用一个migration成功包办三者。

升级先备份、检查schema和扩展版本，明确相邻支持范围；不支持时只读旧结果或使用旧代码恢复。禁止自动清库、猜未知字段、搜索上级目录的私人配置、静默增加权限。代码回滚不等于数据库回滚。

v0.5的本地Memory可以单写入文件实现；升级v0.7存储时测试修订和forget仍生效，不能因记录迁移重新激活旧条目。

## 6. 旧版维护

旧phase只接安全、阻止安装/运行的缺陷及错误样例修复；不持续同步新功能。修复从旧标签建立fix分支，合回对应phase并打新的patch，必要时前向应用main。禁止main整体合回旧phase，使早期版本变成完整平台。

不能保证外部注册表和云模型永久可用。保留锁文件、环境、必要公开产物与已知限制；外部服务改变时明确说明，不重新录制替身替代当年的live证据。

## 7. 每期的最小随附材料

一份演进说明即可清晰覆盖：上版实际问题、功能与责任增量、删除路径、准确运行命令、fixture与环境、正常/失败案例、源码标签、实际验证与未覆盖项。复杂阶段再分scope和verification文件，不为每个小版本强制铺多层文档。

versions.json是计划清单，全部仍为planned；实际发布manifest由实施产生，保存精确SHA/环境/能力。PDF保持私有，文档只用来源指纹、页码和能力摘要。
