## 方向：从已有实践提炼，先完成最小闭环

Open ETF Agent 延续 ETF Agent 已形成的模块职责、实现经验与文章动因：先找原模块和合同，再提取可以独立运行的最小能力。不是另写一套同名系统，再给它配上一篇文章。

- **一个功能版本，一个主模块。** 可以接通既有消费者，但不借“集成”再增加一组 Owner。Owner 指负责该事实的模块，不意味着新服务或 Manager。
- **CLI 优先，API 按消费者需要增加。** 先用真实文件和独立进程完成闭环，再增加必要 HTTP/SSE 读取适配。浏览器界面不作为单个 CLI 模块的前置条件，单独取得资格；API 通过不等于界面通过。已选 11 月 11 日本人云端里程碑则要求下文定义的最小 UI。
- **先复用，后加依赖。** 优先现有代码、Node 标准能力、SQLite 和已采用的 SDK。通用底座可用成熟轻量开源替代；具体选择时核对官方 API、许可证和维护状况，不为小需求引入整套平台。
- **只简化部署，不删核心合同。** 身份、授权、预算、来源、局部失败和未知结果不能随之丢失。模型负责语义判断，Runtime 负责合法执行与真实效果。

[原路线][original-roadmap]中的 Publication、Web、PDF、隔离 Python、合成 ETF、后台执行，应按模块独立完成和验收；可以继续使用 0.10、0.11 等版本，不为一个编号打包交付。既有或已规划的 Decimal、单位、币种、数据截止日与 CSV，不重复算作 1.x 新功能。

## 产品方向：范围更小的真实研究工具，不是永久 demo

**目标：** Open ETF Agent 要能独立支持本人实际研究，包括可私有访问的云端部署。Private ETF Agent 继续作为更完整的自用研究系统；Open 可以通过公开、独立验收的模块逐步靠近其核心能力，不是整套复制，也不把 private 的测试当作公开版资格。本地版仍有价值，但只有本地示例不能满足上云里程碑。两个仓库的研究效益，都不能由功能数量、HTTP 成功或完成部署推出。

当前基线是 v0.10 **已通过离线资格**的执行、来源与交付链。脚本案例用于解释及检验契约，不是最终用户产品的目标。历史 v0.1–v0.5 live runner 不使当前 v0.10 自动具备真实材料/live 资格。下面划分的是结果阶段，不是新版本号，也不授权调整已批准模块顺序：

### 首个真实上云里程碑：明确 go/no-go

测试前冻结具名版本和支持配置。**Go** 必须同时满足：

- 真实操作者入口接受声明的材料类型，调用选定且获准的真实 provider；有证据证明实际获取的来源/结果进入请求及原交付。保留真实成功、失败、unknown 分母，人工检查部分答案，不宣称金融效益已证明。
- 选定阿里云单台 VM 与 Cloudflare Access 边界只允许本人，覆盖 API、下载、备用域名及源站直连检查。实际宿主、订单及配置必须存在并核验；计划或本地模板不是云端资格。
- 原 Session/Run/产物身份和完成结果在正常进程/宿主重启后仍可读。中断中的 Run 行为另验；hot journal 或 unknown 效果未解决时，不宣称可安全自动恢复。不能删失败用例或重置预算/截止时间获得通过。
- 每次支持的升级列明哪些存储数据/schema/Host 版本可读、可写或不能续跑。必要时先完成旧活动 Run，包括现有 tool-host@1 → @2 边界；保留原备份，验证必要数据升级及产物回读。代码回退不得倒退已提交效果或重放模型/工具调用。不支持的兼容性显式拒绝，不静默迁移。
- 在选定配置上实际执行可复现安装、运行、停止、重启和备份恢复手册。凭据不进入公开源码/build；失败、用量、费用记录脱敏但保留分母与原身份。不能把告警阈值表述为计费硬上限。
- 优先争取长期月均基础设施成本低于 30 元；用户允许必要时评估约 60 元/月。最终获准基础设施上限包含主机、存储/备份、网络/域名及支付额外成本，年付金额另列。按用户最新选择，模型订阅费用不计入这项基础设施预算；live 前仍须独立核验套餐限额及禁止超额边界。游客/多用户保持关闭。

缺任一所需证据，就对该支持声明 **no-go**：保持较窄已合格配置、明确阻塞，在相关模块修改后复测。有限值守试点可先于本里程碑，但必须保留较窄标签。不能从版本号或计划表行数算完成百分比，只报告已证明结果与剩余门槛。

## 随模块同步推进部署资格——计划中，2026-10-28

部署是当前同步模块的持续交付切片，不必等齐全部 1.x 功能，也不另建部署平台。这里不声称已经上云或取得当前版本真实模型资格。v0.11 PDF 的代码资格见下方带日期更新；本计划不据此认领上云、当前模型或文章发布完成。

### 首个目标：仅本人、一个持久后端、一个最小交互消费者

- **阿里云后端候选：** 优先评估已有授权的 Linux ECS 或轻量应用服务器、持久磁盘、仓库支持的 Node 26 工具链、显式私有配置和单操作者。Session、产物与共享费用账本放在可替换源码目录之外。沿既有 CLI/Runtime 启动；仅围绕原单 Run Worker 评估操作系统进程监督，不新增 Scheduler 或队列。监督进程重启不能重发结果未知的模型/工具效果。
- **非默认 Vercel 消费者备选：** 小型本人专用静态只读预览可消费显式选定的报告/附件修订，但不在已选阿里云/Cloudflare 关键路径上。模型凭据和 Session 数据库留在后端；仅静态预览不满足已选可用云端里程碑。问答、进度/失败和会话切换的最小 UI 是原入口的独立验收消费者；不能把现有 loopback Reader 原样暴露到公网。
- **不把整个 Runtime 原样塞进 Vercel Function。** 当前官方文档列明函数文件系统只读、可写空间临时、调用有时长上限，所列 Node 为 22/24，而本仓库要求 Node 26。临时文件不是 Session 的持久存储。更长时限或其他 Vercel 产品，也不会自动认证既有 SQLite/Worker 契约。见[函数运行时](https://vercel.com/docs/functions/runtimes)、[时长配置](https://vercel.com/docs/functions/configuring-functions/duration)、[支持的 Node 版本](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions)。
- 阿里云提供[持久云盘](https://www.alibabacloud.com/help/en/ecs/user-guide/quickly-create-and-use-disks/)和[单服务器安装条件](https://www.alibabacloud.com/help/en/simple-application-server/user-guide/create-a-server)。这些只是宿主能力，不是应用正确恢复的证据；选定实例后仍须核验磁盘生命周期、备份和停止/重启行为。
- Vercel Preview 不自动等于私有访问，也不保证与生产服务隔离。部署前核对实际 target 和环境变量，特别是新项目首次部署与生产提升规则。访问控制尚未验证时不发布本人数据；无保护预览不能含私有材料，也不满足仅本人访问的验收门槛。见[部署环境](https://vercel.com/docs/deployments/environments)。执行时重新核套餐和运行时限制；本路线图不创建账号、资源、凭据、域名或付费服务。

**用户已选择方案 2：单台阿里云小型 VM + Cloudflare Access，仅本人使用。** 长期月均基础设施成本优先低于 30 元，现可评估约 60 元/月用于基础设施但不等于自动批准花费；游客保持关闭。配置、地域、购买资格、续费条款和一次付款 99 元的实际订单仍须核验；尚未购买、部署或创建新凭据。下面的已有机器方案仅作非默认备选，不表示用户已有合适宿主。

## 原 1.1 的最小闭环：现由 v0.10 承载

用一个原创合成 ETF 费用或暴露比较作为输入，复用已有确定性计算器：

1. **保留来路：** 原 ResultRef、实际选区、计算输入与派生结果关联起来，不另建金融账本。
2. **证明消费：** 检查下一次真实 Gateway 输入带着同一结果、单位、截止日与限制，而不只检查工具说“计算成功”。
3. **完成交付：** 报告中的结构化数字引用和 CSV 指向同一结果；进程退出后从 CLI/文件读回原字节；需要 HTTP 验证时复用已有 Reader，不把新 API 或网络消费者设为本期前置。

验证尾部关键行遗漏、混币种/不同截止日、分母未知三个反例。坏附件不抹掉独立合法正文；确定性数值核对不认证自由文字的投资论证。

**成功链与关键反例跑通即停。** 如果隔离 Python 尚未独立合格，就先用已有 JavaScript 计算路径，不让本版本再承担一个工作台。

下列文章解释原模块为什么形成。公开提炼保留其核心合同，删去本期不需要的配置与平台依赖；不把原系统的验证记录当成本仓库资格。

| Publication | 稳定块与投递位不随修订改变；提交后失败不抹正文。 | [正文发布的提交边界][publication] |
| ScheduledTaskWorker 的单 Run 切片 | claim / lease / cancel → 同一 Runtime → 原持久事实结算；不照搬 Schedule/Task 平台。 | [定时研究中的有限 Run 与恢复][schedule]；[background 与并发的区别][async-delivery] |
| Result / Reference | 原结果、选区、派生与实际消费分开；来源可回读。 | [计算结果如何进入报告][result] |

每期完成后，在原文章相关论点旁补一个固定代码版本、一条可跑案例和一个失败反例，保留历史背景与未覆盖范围。目标是文章中的机制能够由公开代码解释和复现，不是全文功能对齐。

## 风险、裁剪与验收

**最大风险是把共享准入做成控制平台。** 1.7 只允许一个容量组、两个调用进程和有界队列；未知占用保留原身份，不自动释放、重试或换路。没有真实竞争需求，就整期延后。后续是否加入 Provider 目录、Failover、个人 Profile、Human Park、受控刷新或外部观测出口，分别评估，不捆进已有版本。

RAG的难点是撤权与披露提交顺序，不是先搭向量库。先按声明入口验证真实进程与实际交付字节；已有 HTTP 读取同样核验，SSE 仅在确有消费者时纳入；必要时拒绝整个受保护候选，不增加语义分类器来签发权限。

每个模块完成前，只回答四个问题：

- 输入是否经过真实运行入口，结果能否从 CLI/API 取得？
- 最终消费者是否采用原身份与限制，而非只生成了一个中间对象？
- 取消、重复、重启、局部失败和 unknown 是否在本期范围内可解释？
- 旧的重复入口是否移除，独立合法成果是否仍能读取？

验收聚焦 **Runtime 正确性**；语义状态可保持 `unreviewed`，不另设模型评分门。宣称真实独立模型路径时，仍须有该路径的实际调用证据，不能以 scripted fixture 代替。

历史支持保持窄：固定快照独立可跑、已交付产物可读、必要相邻数据升级保留原备份；失败或未知状态不破坏旧库。旧活跃 Run 默认不跨版恢复。不扩展多租户、交易执行、不可信插件安装、集群容灾或普遍 exactly-once。

原始规划及边界见[原路线][original-roadmap]与[能力矩阵][original-matrix]；不从版本号反推完成状态。
