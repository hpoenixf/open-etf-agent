# 07 · 执行顺序、交接与版本文章

> 本次交付只是一份可评审方案。实现、阶段标签、软件发行和文章发布均需沿后续具体任务执行，不因本文件存在自动发生。

## 1. 可以何时开始

方案评审结束并确定最小源码/数据的公开权利后，即可开始 v0.1，不需要等待原系统所有 Owner 完成验收。每个后续版本只等待自己的真实前置条件，不以“全系统都成熟”作为无限期阻塞理由。

原先的一到两天目标只适合集中实现极小闭环，不用于承诺从 v0.1 到 v1.0 的交付日期。实现速度、机制成熟、真实模型语义质量和公开发布是四个不同判断。

## 2. 最先执行的 v0.1 任务包

| 次序 | 工作 | 完成物 | 不越界的约束 |
| --- | --- | --- | --- |
| 1 | 固定本期范围与工具链 | phase/v0.1，README、环境与依赖锁 | 不提前建 v1.0 目录树或选全部 SDK |
| 2 | 编写独立合成 fixture | 两版短手册、明确差异、计算期望 | 不拷贝书稿原文、私人文档或客户资料 |
| 3 | 实现最小 Host | read_document、确定性计算、Schema、调用回执 | 不加 shell、交易或任意文件系统访问 |
| 4 | 接通 Gateway 与 Loop | fixture/live 共用循环，有限重试/预算/取消 | 不写第二套演示执行流 |
| 5 | 做用户可运行交付 | CLI、默认 demo、错误输出和退出码 | 不声称已经具备浏览器、恢复和发布版本 |
| 6 | 完成本期验证与说明 | 契约检查、真实往返记录、演进与限制 | 真实服务调用另受实际授权与成本约束 |
| 7 | 提交阶段 PR | 精确 diff、最后候选证据、README | 不自行合并 main、打标签或宣告稳定 |

三个核心 Module 可以先写成少量文件。遇到依赖注入需求时，用函数参数或小对象即可；不要为将来的八个核心建立一个预设框架。

## 3. 后续版本的主要依赖

| 版本 | 开始实施前必须稳定的前置 | 本期特别需要避免的旧习惯 |
| --- | --- | --- |
| v0.2 | 工具描述与执行绑定、一次调用身份 | 在模型循环里加入 MCP/Skill 专用分支 |
| v0.3 | 两种真实工具接入与方法读取 | 先建庞大 Plugin Manager 再找用途 |
| v0.4 | 工具回执和来源身份能区分 | 把 messages 当永久事实库 |
| v0.5 | 可序列化结果、调用与版本绑定 | Recovery 导入全部业务内部类型 |
| v0.6 | 持久事务与恢复合同 | 把模型 token 流直接等同已发布正文 |
| v0.7 | Root生命周期、持久身份、发布事件 | 复制第二套子代理 Runtime 或让页面持有后台任务 |
| v0.8 | 结果回读、Context、Checkpoint | 把摘要、记忆和授权混成同一种事实 |
| v0.9 | Tool、Result、Artifact 与安全准入 | 为方便演示直接开放宿主 Python/shell |
| v1.0 | 所有拟声明能力的实际候选资格 | 在最后一版重新进行一次大规模架构重写 |

同一期内部可以并行编写独立 fixture、文档与 Adapter，但修改同一核心契约时需由明确的集成人协调。不要同时开启十个阶段，让各 Agent 分别想象未来接口再相互覆盖。

## 4. 每次迁入成熟机制的简短说明

实施 PR 填写以下内容即可，不需要新建复杂管理系统：

```text
要解决的用户问题：
本期保留的最小行为：
参考的公开资料／可公开设计依据：
本次明确不搬入的历史复杂度：
新增或改变的公开接口：
预计需要修改的非本模块位置及原因：
必须保留的不变量：
成功、失败、取消／恢复的目标场景：
删除或替换的旧路径：
最终候选 SHA、验证范围与尚未验证项：
```

私有工程经验可以用于判断，但不能把私人 evidence、载荷、内部链接或完整源码直接贴到公开 PR。已知失效模式应独立构造合成复现。

## 5. 实施 Agent 的接手提示模板

以下是后续任务模板，需把版本填成明确的一期；不是现在开始自动开发的命令。

```text
在 hpoenixf/open-etf-agent 中，仅实现指定版本 vX.Y。

先读取 docs/plan/README.md、对应版本范围、架构契约、分支政策与验收说明。
读取当前代码和前一版本的实际发布记录，不假设路线中的能力已经存在。
从已验收主线创建/使用 phase/vX.Y；保护已有未提交修改与其他人的工作。

本期必须独立安装和运行，默认 demo 不依赖私人服务或模型密钥。
fixture 与 live 必须共用 Runtime。只实现本期真实需要的接口；不预建未来模块。
迁移设计认识和合成失败案例，不复制私人书稿、生产数据、未经授权代码或凭据。

先跑通同一个基础案例，再实现本期新案例及必要失败路径。
确定性结构调整使用契约验证；模型语义变化使用最小充分的目标任务。
付费模型、对外数据发送、发布部署均遵守具体授权，不由路线文档自行扩权。

更新本期演进说明、支持范围、准确命令、删除路径和最终候选验证记录。
未实现、mock-only、partial、unknown、unreviewed 必须如实标注。
仅提交本期 PR，报告精确分支/commit/验证与阻塞；未经批准不合并、不发布。
禁止顺手修改 Lab、私有产品或书稿仓库，也不要自动推进下一期。
```

## 6. 每一期怎样写成一篇有代码的文章

文章跟随已经完成的机制，不先写“我们已经实现”再让代码追赶。每篇绑定该版本固定标签，提供上版到本版的 compare、一个共同任务、一个新能力案例和一个真实失败路径。

| 版本 | 建议文章主问题 | 最重要的演示 |
| --- | --- | --- |
| v0.1 | 一个 Agent 最少需要什么，工具调用怎样真正发生？ | 同一 Loop 的直接回答、工具成功和拒绝 |
| v0.2 | 方法与外部工具为什么不该长进模型循环？ | 换 MCP 读取，按需加载 Skill，循环不变 |
| v0.3 | 怎样增加一个领域扩展，再把它干净移除？ | 文档包与 ETF 包的注册、失败回滚和释放 |
| v0.4 | 为什么上下文不该保存所有研究事实？ | 检索、展开原文、引用、外置结果再读回 |
| v0.5 | 进程死后，哪些事情能继续，哪些不能重做？ | 新进程恢复、已结算去重与 unknown |
| v0.6 | 从答案生成到用户可见，中间到底有什么？ | 预览、提交、断线重连、历史与附件 |
| v0.7 | 子代理与后台运行分别解决什么问题？ | 独立模型 Child、后台 A 与短问 B |
| v0.8 | 怎样让历史变短，却不让事实消失？ | 压缩后回读、显式记忆与忘记 |
| v0.9 | Web、PDF、Python 如何共享来源与产物身份？ | 有界工具链和失败时保留部分交付 |
| v1.0 | 怎样证明一个小内核能持续演进？ | 全链复现、扩展替换、已知限制与评估 |

建议统一结构：上一版本的实际限制 → 最小新增机制 → 前后调用图 → 一次可运行输入/输出 → 故障与边界 → 哪些旧实现被删除 → 固定版本/代码入口。

新系列可总称“Open ETF Agent 演进实录”。六层全景 V3 仍作为完整请求地图，不删除或改写旧版；新文章解释哪些层在本期真正成立。教材继续由 Lab 承担教学配套，Open ETF Agent 提供工程演进路线，不把两个仓库重新绑成相互运行依赖。

文章发布沿既有隐私、分类与双语约定另行执行。本次只提供选题和绑定规则，不向博客、阅读站或其他仓库发布正文。

## 7. 限制范围的四个决策规则

**模块不够成熟**：先留在研发/Lab，不因为版本号到了就晋升；可在路线中标明原因。

**一个版本过大**：优先拆同一阶段内部的实施 PR 和验证步骤；若必须新增里程碑，显式修订计划清单、版本映射和章节覆盖，不暗中改变 v0.1 的定义。

**外部服务不可用**：完成仍有意义的离线契约工作，live 资格保持未验证，不生成假的成功记录；默认版本不绑死私人服务。

**要靠多个核心特殊分支才能接入扩展**：先复核 Interface 和依赖方向，删除不必要的转发层；不通过引入新的全能管理器掩盖耦合。

## 8. 方案评审应确认的重点

本提案建议采用：三个核心起步；Skill/MCP 在 v0.2；v0.6 首次完整 Web 六层；v1.0 覆盖基础篇的有界运行能力和工程原则；每期保留完整分支及固定标签；只读合成金融案例；本机单用户为明确产品边界。

精确 SDK/Node 版本、许可证选择及可用真实模型属于相应实施/发布的实际输入，不在本方案中虚构已确认值。它们不阻止评审设计，但在真实安装、模型调用和正式许可发布之前必须落实。

本方案通过后的直接下一步是实现并验收 v0.1，而不是同时复制几十个模块，也不是先创建十套目录和分支。
