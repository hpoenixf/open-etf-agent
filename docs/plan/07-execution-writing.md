# 07 · 实施顺序、接手说明与文章演进

> 仅实施明确授权的一期；方案存在不等于授权自动合并、发布、付费调用或修改其他仓库。

## 1. 最先做什么

方案评审后从v0.1开始，不等待私有产品全部成熟，也不同时开启十个phase。先取得最小源码/数据公开权利，锁定工具链，独立编写合成资料，接通读取/模型/保存，再验证文件可读和来源可查。

原先一到两天只能是极小实现的尝试范围，不承诺整个路线或稳定性验收的工期。版本按结果发布，不按日期凑数。

### v0.1的最小工作包

| 步骤 | 交付 | 边界 |
| --- | --- | --- |
| 输入与fixture | 原任务、两版资料、页码/版本、四题期望 | 只使用独立合成资料和明确许可的内容 |
| Host与工具 | read_page、确定计算、save_report、调用回执 | 受限目录，无任意shell |
| Gateway与Loop | fixture/live共享往返，有限预算/取消 | 一种声明协议，先不建全部Adapter |
| 可见结果 | report.md、manifest、JSONL、实际读回 | 保存不等于恢复，不先建SQLite |
| 验收与说明 | 正常/失败、来源/文件核对、本期演进说明 | 真实模型质量另审，不数模块证明成熟 |
| 提交 | phase/v0.1到main的PR | 未授权不合并、不打标签、不自动做下一期 |

## 2. 真实依赖，而不是旧系统的继承顺序

Skill依赖普通读取工具，不依赖Plugin。Hook依赖清晰调用时点，不依赖热更新。单进程Child依赖共享预算、范围和回执，不依赖后台/lease。压缩依赖来源回读，不依赖完整Run恢复。Memory需要可靠本地保存和显式范围，不必先建多用户服务。报告需要确定字节和来源，不必先有SSE。

只有当原Run需要跨进程接续时才进入v0.7；只有运行要脱离连接、界面要并发交付时才进入v0.8。这些区分是本次重排的核心。

## 3. 每期交接的最小信息

写清用户问题、输入/输出、参考的公开机制、所属运行配置、要保留的不变量、真正需改的非本模块位置、将删除的旧路径、正常与失败验收，以及候选SHA/未验证范围。

多个执行者可以分别做fixture/工具/界面，但公共类型和装配由一个明确集成人维护。先接通一条主线再并行，不让十个Agent各自想象未来接口。

### 接手模板

```text
仅实现 Open ETF Agent 的指定版本 vX.Y。
先读 docs/plan/README.md、对应阶段、05能力覆盖矩阵和架构契约。
按基础、工程和研究配置明确支持范围；以本仓库接口、示例和证据为准，不把计划当实现。
读取当前main/前一已发布标签和现有工作，再使用phase/vX.Y。

本版本必须完整独立运行，不能依赖私人服务、未公开资料或上一分支。
fixture/live共用Runtime；不得把批量读取、mock PDF或宿主子进程冒称独立Agent、真实解析或沙箱。
先复现共同文档任务，再实现本期增量与失败路径。
需要来源、回执、字节时真实记录；未知、不支持、未评审如实保留。
确定性改动做针对性回归，模型语义变更做获准的小样本观察。

新结构接管后删除旧执行路径，旧报告按其原身份保留只读兼容。
更新准确命令、边界、版本文章入口和最终候选证据。
仅提交本期PR；不合并、不发布、不调用未经授权服务、不修改其他仓库。
```

## 4. 文章与版本绑定

| 版本 | 主问题 | 必须展示的变化 |
| --- | --- | --- |
| v0.1 | 极简Agent如何交出第一份有出处的报告？ | 读取→比较→保存→读回；提议与回执 |
| v0.2 | Skill和MCP为何不要求新的Loop？ | 同一任务换读取Adapter，方法按需读取 |
| v0.3 | Hook与分工怎样留在明确范围内？ | 回调时点；批量worker与模型Child分别展示 |
| v0.4 | 从候选到原文，再到模型输入发生了什么？ | 查询改变、真实回读、外置与引用 |
| v0.5 | 摘要和记忆为什么不能当作原始事实？ | 净容量、回退、修订、忘记和未来投影 |
| v0.6 | 用户是否真正拿到了报告？ | reader、来源、下载、四题检查、变化表CSV |
| v0.7 | 哪些事实必须跨进程保留下来？ | 可信包快照、真正冷恢复与unknown |
| v0.8 | 页面不再占有任务以后，怎样连续交付？ | Web六层、后台A/短问B、SSE/History |
| v0.9 | 研究工具如何保留输入与派生产物来路？ | 真实HTTP/PDF/容器、独立ETF扩展 |
| v1.0 | 怎样证明演进没有把小内核拖垮？ | 实际diff、扩展替换、各配置资格和限制 |

每篇从上版真实问题写起，给共同任务、新增任务、失败路径、被删除代码、固定标签和compare入口。完整解释可写新文章，但本次只提交选题计划，不发布博客正文。新文章沿既有隐私/双语约定另行执行。

六层采用公开请求视角，观测与评估跨层参与。文章解释本仓库真实发生的改动，不把其他项目的并列示例说成这里已经完成的历史迁移。

## 5. 范围与阻塞处理

机制不成熟：留候选/研发，不因版本名晋升。外部服务不可用：完成可验证的离线部分，live保留未验证。阶段过大：拆本期实施PR，若更改版本承诺同步矩阵和清单；不要暗中扩张v0.1。扩展牵动多个核心：先检查Seam和重复事实，不能再加一个全能Manager。

保留v1.0的既定能力目标，按实际依赖逐步交付。许可证、精确依赖、可用模型及费用授权在实施/发布前落实；本方案不虚构已确认值。
