# Upgrading an existing installation

English | [简体中文](upgrade-guide.zh-CN.md)

## v0.10: an intentional execution-protocol boundary

v0.10 uses `tool-host@2`. A persisted `tool-host@1` snapshot is rejected with `UNSUPPORTED_HOST_SNAPSHOT_VERSION`; no automatic migration, missing-digest fallback or tool re-execution is provided. This also applies to attempts to replay a terminal Run through Runtime: completing an old Run does not make its Host restorable by the new Runtime.

Retained output has separate Result, Artifact and Publication readers. Readability through those interfaces is distinct from resuming execution, and is not permission to rewrite or delete the original data. See the [original reviewed contract](https://github.com/hpoenixf/open-etf-agent/blob/e442f600891be79625fc78751e2d9f39905920da/openspec/changes/result-reference-consumption/design.md) and [implementation lineage](evolution/result-reference-consumption-lineage.md).

## Operator release checklist

This checklist is an operational condition, not an implemented deployment-wide preflight, automatic drain or migration command.

1. Record the installed and candidate code versions, dependency locks and their supported stored-data and Host versions. Stop new admissions before replacing an installed version.
2. Let active Runs finish on their original Runtime. If that is not possible, isolate the entire old deployment and its data instead of silently switching those Runs to the new Runtime. Retain the matching original code, dependencies, configuration and backups. Isolation preserves recovery options; it does not override original deadlines, unknown effects or other recovery restrictions.
3. Do not point old and new Workers at the same live Session, rewrite snapshot version labels, or use a new Run to pretend the old Run resumed. Preserve original backups and committed outputs. Do not rewind committed effects when rolling back code or configuration.
4. Before calling an upgrade supported, rehearse the applicable upgrade and rollback path on isolated synthetic data, including independent original-output readback. An incompatible or uncertain state blocks that upgrade; do not turn refusal into an invented terminal success or failure.

The [cloud go/no-go checklist](plan/v1-to-v2.md) retains these requirements. No cloud deployment or unattended rolling-upgrade capability is claimed by this document.

## What the existing test establishes

The [compatibility test](../test/result-consumption-delivery.test.mjs) changes a current synthetic Host snapshot's version to `tool-host@1`. It checks refusal before execution, unchanged original Session and files, independent Artifact readback, and supported `tool-host@2` continuation. A controlled version change between inspections is also rejected before claim; that is not an atomic cross-version migration guarantee.

This test is not a snapshot generated by the old Runtime. Real old-version recovery and every historical output format remain unqualified by that test. The Runtime preflight protects a selected Run; it does not inventory all deployed Sessions or prove that an operator has retained a usable old deployment.
