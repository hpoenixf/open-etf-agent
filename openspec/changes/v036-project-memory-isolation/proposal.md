# A26: Project Memory operator lifecycle

## Why

A one-off analysis should be able to turn Memory off; a repeat analysis
should be able to use only the approved preference revisions. Existing
Project tasks always attach the same broad lexical Memory surface when the
capability is enabled. Existing explicit save/revise/forget cannot express
a reversible pause, and status inspection before and after recall is limited.
Do the complete bounded operator lifecycle together rather than release each
of these pieces separately.

## One owner

Keep the one local project Memory library, versioned records and original
consent-bound write authority. Add exact selected-recall admission, temporary
isolation, pin/unpin, pause/restore, and inspectable current status and use
receipts. Reuse Project scheduling of this one ordinary Run, the existing
Session, Admission, Memory projection and normal report readback. There is
no new library, profile/identity service, model gateway or scheduler.

The [public Memory article](https://hpoenixf.com/eff-agent-article/articles/026-agent-memory-forget-durable-effects)
separates permission, persistent writes, recall in the actual request, and
future exclusion after revision or forgetting. This local implementation is
a bounded public counterpart, not full service parity.

## Boundaries

No automatic learning, new approval store, semantic retrieval/embedding,
account/global Memory, temporary Conversation, physical erase, browser or
deployment work. Explicit modes apply to ordinary research (not schedule,
Child or trusted-tool composition); selected mode initially excludes managed
compaction. A temporary run still persists its normal task, checkpoints and
report. An old default task still uses its existing broad opt-in Memory
authority. Currentness protects typed Memory materials, not arbitrary free
text or a provider request that already went out.
